01The Threat Model — What a Website Can Actually See

Why this section exists

Every design decision later in this document is downstream of three physical facts. Get these wrong and you build security theater. Get them right and the rest follows almost mechanically.

  • Layer 2 dies at the first router. Your MAC address is a link-local identifier: your machine sends it to your router, your router replaces it with its own on every hop to the internet. No website has ever seen your MAC. Rotating it for web scraping is a ritual, not a defense — so we don't do it, and we say so in the code.
  • Layer 3 is the gate. The exit IP is the one identity a target must observe. Every mechanism here rotates, prices, and protects IPs — because that is the only lever that exists.
  • "Blocking Tor" is a lookup, not a detection. Tor exit nodes are published lists. A target downloads the list, matches your IP, drops you. Disguising the browser as Chromium fixes the fingerprint (layer 7) but cannot fix a gate (layer 3). This is why our Tor mode is paired with failover and hybrid pooling rather than relying on disguise alone.

The historical bug that started this project: the UI collected a proxy list, the mode said "Rotating", but the adapter read proxies[0] every single time. One IP for an entire 500-page run. The user believed they were rotating; they weren't. The 91/91-failed Yelp run was exactly this. Lesson one of the whole document: an anonymity feature that isn't exercised is indistinguishable from no anonymity feature.

02The Trust Ledger — Beta(α,β) Posteriors

Why not just count successes

Each identity in the pool holds a posterior distribution over its own block probability, modeled as Beta-Bernoulli: blocks are Bernoulli trials with unknown parameter p, and the Beta family is the conjugate prior, which means updating is just counting:

EQ. 2.1 — The update rule (the entire "AI" is these two lines)
# after each request through identity j: α_j ← α_j + 𝟙[success] β_j ← β_j + 𝟙[block] E[blocked_j] = α_j / (α_j + β_j) # posterior mean = trust score

Why the +1/+2 Laplace prior: an identity with zero history gets (0+1)/(0+0+2) = 0.5 — neutral, slightly suspect. This is deliberate. A brand-new IP that has never been tested is not a proven ally; giving it full trust is how you feed your best traffic to a dead proxy. Skepticism toward the unknown is a feature.

Why a distribution and not a bare ratio: a ratio (5 successes / 5 failures = 50%) treats five data points the same as five thousand. The Beta distribution's concentration — α+β — encodes how much evidence you actually have. Early counts wobble, late counts stabilize. In production we use the posterior mean for selection, and the concentration is what stops one unlucky 403 from demoting a veteran identity.

Worked example — two identities, same ratio, different evidence
IdentityHistoryE[blocked]Reads as
p14 ok / 4 blocked50.0%"coin flip, barely tested"
p2400 ok / 400 blocked50.0%"genuinely burned, avoid"
p3196 ok / 4 blocked2.5%"workhorse"

03Weighted Selection — The Pool Re-Ranks Itself

Why not round-robin

Round-robin gives every identity equal traffic regardless of quality. That is optimal only when all identities are equal — which they never are. Selection is a categorical draw with posterior-weighted masses:

EQ. 3.1 — Weighted pick (the one line that replaced the broken proxies[0])
weight_j = 1 − E[blocked_j] pick identity j with P(j) ∝ weight_j # random.choices(weights=...)

The consequence is economic, not algorithmic: a 95%-clean identity carries roughly 10× the load of a 50% one. The pool is a portfolio that rebalances itself after every request. Bad identities fade toward zero traffic while still being periodically re-tested (they never hit exactly zero, so recovery is possible when a target's mood changes).

Why this compounds over a run: early on, everything is ~50% and selection is nearly uniform — correct, because we know nothing. As evidence accumulates, the distribution sharpens. The system's information and its behavior stay in lockstep at all times. That property is called matching, and it's the same force behind multi-armed bandits — we're running a lightweight bandit where the arms are IPs.

04Cooldown — Suspension, Not Execution

Why we stopped deleting blocked identities

The naive move on a block is to remove the identity. The correct move is a 300-second bench (a cooldown timestamp, blocked_until). Reasons, in order of importance:

  • Most blocks are temporary. Rate-limit windows expire. A 403 at 10:40 usually forgives by 10:45. Deleting the identity throws away a working asset because of a timeout, not a ban.
  • Pool depletion is the death of long runs. In a 2000-page crawl with aggressive targets, discard-on-block empties the pool in the first hour. Cooldowns keep the pool sized; it rotates people to the bench instead of off the team.
  • Re-testing is information. A cooled identity that succeeds on return earns β→ posterior recovery. The ledger self-corrects in both directions.

Edge case, handled explicitly: if every identity is on the bench, we don't fail — we pick the one whose bench time ends soonest. starving the job is worse than reusing a slightly-warm identity.

05Sticky Identity — Humans Don't Re-IP Mid-Sentence

Why per-request rotation is itself a signal

Here is an uncomfortable truth: rotating the IP on every single request to the same site is itself bot-like. A human reading a directory keeps one connection path for their whole session. A crawler that appears from a different country on every page load is describing itself perfectly to anyone logging patterns.

So the ledger remembers each domain's sticky identity — the one that last succeeded there — and reuses it with probability s = 0.7:

EQ. 5.1 — The stickiness operator
P(reuse sticky_d) = 0.7 # if eligible (not cooled) P(any other) = 0.3 # weighted by posterior, as in EQ 3.1

Why 0.7 and not 1.0: full stickiness recreates the original problem (same IP forever). The 30% churn keeps the ledger sampling the other identities on this domain — maintaining its information — while still presenting a mostly-consistent route. Why this survives rotation: the stickiness is per domain, so rotating across domains (where it's safe) happens at full speed while per-domain behavior stays human-shaped.

06Persona — An IP Without a Fingerprint Is a Disguise That Doesn't Fit

Why the UA must be derived, not random

A new exit IP arriving with last year's fingerprint is a red flag: real humans carry consistent browsers. Each identity therefore owns a persona — useragent + locale + timezone — and the choice is deterministic from SHA-256 of the identity key:

EQ. 6.1 — Deterministic persona assignment
persona_i = POOL[ SHA256(key_i)[0] mod 8 ] # same key → same persona, forever

Why deterministic hashing instead of random.choice at request time: randomness means identity #3 is Chrome in New York at 10:00 and Firefox in Berlin at 10:01 — a walking contradiction. Determinism means the pair (IP, persona) is a stable joint identity. The engine ships eight internally-consistent profiles (real modern UA strings with matched locale/timezone), so there are no impossible combinations like a Mac UA with a Windows platform leak.

Where it plugs in: browser engines take useragent / locale / timezone_id natively; curl-cffi gets the UA via headers. Tor hops additionally force block_webrtc=True — WebRTC STUN dials around SOCKS tunnels and would leak the real IP to the target, which quietly defeats everything else on this poster.

07AIMD Pacing — Steal the Oldest Honest Algorithm on the Internet

Why TCP congestion control solves our problem exactly

TCP solved a mathematically identical problem in 1988: send into a link whose capacity you cannot observe, where exceeding it is catastrophic (packet loss) and underusing it is wasteful. Its answer — Additive Increase, Multiplicative Decrease — maps one-to-one onto scraping: capacity = the target's rate limit, packet loss = 403.

EQ. 7.1 — The per-domain delay recursion
d_{t+1} = clamp( d_t · (0.9)^{𝟙[success]} · (2.0)^{𝟙[block]} , 250ms, 30s )

Why multiplicative down and multiplicative up (not additive): the danger is asymmetric. Slowing too little gets you blocked (expensive, visible); slowing too much just wastes time. ×2 on a block makes the cost of over-speed exponential — you converge from above fast. ×0.9 on success makes speed gains cautious and reversible — you approach the ceiling from below slowly. The fixed point sits just under the target's true threshold, and the system finds that threshold without ever being told what it is.

Worked example — finding Yelp's patience in ~15 requests
EventDelayWhat the engine believes
start1.50signorance — the designed prior
5 × success0.88s"this domain tolerates more"
block1.77s"too fast — back off hard"
4 × success1.16s"ease back in"
steady state~1.2-1.4soscillating just under the limit

Each domain converges to its own operating point: a sleepy site drops toward 250ms, a hardened one stabilizes near 8s. Same code, no configuration, per-domain memory.

08The Burst Pacer — Timing Is a Fingerprint Too

Why uniform randomness is still uniform

Common wisdom says "add random jitter to your delays." Counterpoint: uniformly-jittered gaps are still a flat distribution, and flatness is detectable with one variance test. Real human traffic is not flat — it is bursty: a page loads, three resources follow within seconds, then silence while the human reads. This is the classic domain of the Poisson cluster process:

EQ. 8.1 — Two regimes, probabilistic transitions
# inside a burst (page-load momentum): gap ~ Exp(λ=0.8/s) # mean ≈ 1.25s — rapid follow-ups # quiet stretch (human is reading / afk): gap ~ Exp(λ=0.05/s) # mean ≈ 20s — genuine silence # regime switches are probabilistic (p_enter=0.15, p_exit=0.08)

Why this beats jitter: the signal a detector computes on inter-arrival times — mean, variance, autocorrelation — looks like logged-in user sessions, not like a scheduler. Related to the Hawkes self-exciting family (bursts = excitation, silence = decayed excitation), but implemented as an explicit two-regime process because it is simpler, inspectable, and has no hidden clock state to desync — engineering honesty over mathematical flex.

Composition rule: the burst gap is floored by the AIMD delay. A domain that just pushed back stays slow even inside a burst — the pacer shapes the texture, the controller holds the safety margin.

09The WAF State Filter — Leave Before the 403, Not After

Why a block is the most expensive possible measurement

A 403 is information — but it is the most expensive kind: you paid a burn identity + possible escalation + log noise to learn it. Targets telegraph before they block: latencies creep, soft challenges appear, error mixes shift. We fold those cheap signals into a single state estimate in log-odds space:

EQ. 9.1 — The state update (log-odds of "this domain is about to bite")
ℓ ← clamp(ℓ + +1.2·𝟙[403] + +0.7·𝟙[429/spike] + −0.35·𝟙[clean] , −4, +8) P(red) = 1 / (1 + e^{−ℓ}) # latency spike = latency > 2.5 × median of last 12 # BREAKER: P(red) > 0.80 → park the domain 20 minutes, pool moves on

Why log-odds and not a probability bar: addition in log space is a Bayesian update for independent evidence — each signal nudges the estimate multiplicatively, early evidence moves it fast, and the clamp bounds pathological runs. Why 0.8 and not 0.95: the last stretch between "almost certain" and "certain" is where blocks actually print. Withdrawing at 0.8 means acting while the estimate is still cheap — that is the entire point of a circuit breaker in electrical engineering, borrowed wholesale: open the circuit on prediction, not on fault.

What it buys in numbers: a typical escalation costs 2-3 burned identities; a park costs 20 quiet minutes. Against a 500-page target, trading a fifth of an hour for three identities is a profitable trade every single time.

10Failover — A Block Is a Statement About the Identity, Not the URL

Why retrying on the same IP is arithmetic, not persistence

When a block lands, the naive crawler retries identically — same IP, same fingerprint, same timing — and is surprised by the identical result. The engine instead rotates immediately, on the error path, before the retry fires:

EQ. 10.1 — The failover jump and its invariant
skip = min(2, n − 1) new_identity = pool[(i + skip) mod n] # INVARIANT: (i + skip) mod n ≠ i ⟺ skip mod n ≠ 0 # guaranteed because 1 ≤ skip ≤ n−1

Why min(2, n−1) exactly: the upper bound is forced by the invariant — jumping exactly n laps back to the blocked identity. Taking 2 (when the pool allows) skips the previous identity too, which was likely blocked in the prior wave. A drift guard re-advances if the pinned identity somehow equals the blocked one — defensive coding for desync between the rotator's counter and the pinned entry.

Tor failover is NEWNYM: when the blocked identity is the Tor endpoint, we don't skip — we signal the daemon (SIGNAL NEWNYM on the control port, cookie-auth first, password fallback). Tor rebuilds its circuit: new Guard→Middle→Exit path. With |E| ≈ 1000+ live exits, P(new exit ≠ old) ≈ 1 − 1/|E| ≈ 99.9%. One control-port command converts "we are blocked" into "we are someone else."

Retry success is geometric — if a random identity is clean with probability q:

EQ. 10.2 — Geometric retry success
P(success within k tries) = 1 − (1 − q)^k # q=0.8: k=1→80%, k=2→96%, k=3→99.2%

11Hybrid Pooling — When They Blocked Every Tor Exit

Why the answer to IP blocklists is diversification, not disguise

Hybrid mode merges the user's proxies and the Tor endpoint into one rotation pool. If a fraction f of the pool is blocked (say the target lists every public exit), a double failure requires two independent draws into the blocked set:

EQ. 11.1 — The quadratic collapse of failure
P(request hits blocked) = f P(retry also hits blocked) = f² # independence does the work # f = 0.2 (every Tor exit listed, 20% of pool): first draw fails → 20% retry fails too → 4% # vs 100% on a tor-only run

The thesis in one sentence: independence between identities converts a likely, repeated failure into a rare, quadratic one. Tor's exit IPs stop being a single point of failure and become a per-request tax that shrinks with every retry. This — not browser disguise — is how you walk through a site that blanket-blocks Tor.

12Response Cache — The Best Request Is the One You Don't Send

Why ETag/304 beats every stealth trick on this poster

Every stealth mechanism manages the probability of getting caught. The cache removes the question. First fetch, store the body plus the target's validators (ETag, Last-Modified). Later runs send a conditional request:

EQ. 12.1 — The two-tier hit model
FRESH (age < TTL) → serve from cache. zero requests leave the machine STALE + validators → GET with If-None-Match / If-Modified-Since → 304 Not Modified: serve cached body (no content transfer) → 200: fresh body + new validators stored

Why 90% is the realistic number: directory listings and business pages change on the scale of days; a re-run the next morning re-fetches almost nothing. Every cache hit is a request the WAF never saw — which improves every other number on this poster for free. The implementation stores a Selector-compatible wrapper so extraction code cannot tell a cache hit from a live fetch.

13Sitemap-First & Pre-Flight Probe — Cheaper Pages, Fewer Corpses

Two small ideas with outsized returns

Sitemap-first. The search/listing pages of a directory are the most protected pages on the whole site — the WAF is tuned for exactly the crawling pattern they invite. But the same site publishes sitemap.xml: static, CDN-served, no protection, no rate limiting, containing hundreds of per-business detail URLs. Three requests against an unarmed file replace fifty against a wall. Include/exclude patterns and a domain filter keep the harvest clean.

Pre-flight probe. Before the job: one cheap parallel request per proxy (8 workers). Dead entries leave the pool at t=0. Without this, dead proxies surface mid-run as mystery failures that pollute the very statistics the ledger learns from — a dead proxy looks identical to a blocked one to a Beta update. Clean inputs, clean inference.

14Cross-Run Memory — The Ledger Lives in logy.db

Why this is the design decision everything else serves

All four ledgers — identity posteriors, domain delays, sticky maps, WAF states, response cache — persist in the same SQLite database the app already uses. The consequence is structural:

Run 10 starts where run 9 ended — not where run 1 started.

Yesterday's Yelp run learned which of your seven proxies get burned after twenty pages, at what delay the 403s begin, which exits are listable. Today's run loads all of it in one _load() and starts from experience. This is the difference between a tool and a system: a tool executes a strategy; a system accumulates one. Mainstream open-source scrapers ship engines; none of them ship memory.

15Honest Limits — Where the Math Stops

Because a design doc without failure modes is a brochure
  • Behavioral fingerprinting is out of scope. Mouse entropy, request ordering, JS execution timing — the stealth browser's job (Scrapling's Chromium stealth, Cloudflare solving), not the ledger's. The two layers compose; they do not substitute.
  • The worst case is priced in. A target that blocks every exit and every datacenter range leaves residential proxies as the only route. That is why the ops checklist leads with them.
  • Mild risks: sticky identity concentrates evidence on one route (mitigated by the 30% churn); AIMD can be goaded into oscillation by a randomizing adversary (bounded by the clamp); the Beta posterior is only as honest as the block detector — which is why looks_like_block() is deliberately conservative and 404s never trigger it.
  • Native PoW solving (Anubis-style) exists as an experimental module: detection + the sha256 leading-zero-bits solver, unit-tested against synthetic challenges. Wiring the full handshake needs live targets — declared as such in the code, not hidden.
